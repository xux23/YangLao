## 〇、一页速查（进场前 60 秒看这里）

**一句话定位**：面向中小型养老机构的 B/S 管理系统，管理员/护理人员/家属三类角色协同，覆盖老人档案、护理、健康（含用药任务闭环）、探访留言四大业务加系统管理，共 5 个模块。

**规模数字**（别说虚的，就报这些）：
- 后端 Spring Boot 3.2.5 + MyBatis-Plus 3.5.5，79 个 Java 文件约 4400 行，48 个 REST 接口，8 张 MySQL 表 + Redis（7.x）三类安全数据；
- 前端 Vue 3 + Vite 5 + Element Plus + Pinia + ECharts，14 个页面约 3900 行；
- 自带接口回归脚本 `test_api.js`：68 项断言，覆盖鉴权、锁定、黑名单、越权、全部 CRUD 与统计导出；演示数据 100 余条、日期全部相对当天生成。

**架构链路**（会画图就画）：

```
浏览器(Vue3/Axios 带 JWT) → 8080 /api → JwtInterceptor(验签→查黑名单→取角色→比对@RequireRole)
  → Controller → Service(事务/业务规则/数据隔离) → MyBatis-Plus → MySQL 8
                                    └→ RedisService → Redis(验证码/失败计数/令牌黑名单)
```

**三角色**：admin 全部功能；nurse 档案/护理/健康/用药/探访审核/留言回复；family 只看自己关联老人的数据 + 提交探访预约和留言。

**演示账号**：admin / nurse01 / family01，密码均 123456（登录需图形验证码）。

## 一、项目陈述类

### Q1.1 请简单介绍一下这个项目（1 分钟版）

**参考答案**：这是我独立设计并开发的一个养老机构管理系统，采用 Spring Boot + Vue 的前后端分离架构，解决中小型机构手工记录、家属沟通不畅的问题。系统分五个模块：系统管理、老人档案、护理管理、健康管理、探访管理，管理员、护理人员、家属三类角色按权限协同使用。技术上我比较有三个特色的地方：一是登录安全接入了 Redis，做图形验证码、连续失败锁定、登出令牌黑名单；二是用药任务实现了"计划—按需生成—确认—逾期提醒"的闭环，不依赖定时任务；三是家属数据做了服务端强制隔离，防水平越权。项目自带 68 项断言的接口回归脚本和演示数据，可直接现场演示。

> 3 分钟版：在 1 分钟版基础上，展开讲一个你最有把握的模块（建议用药闭环，见第六章），再讲测试与数据设计（第九章）。

### Q1.2 为什么选这个题目？

**参考答案**：老龄化是现实趋势，"十四五"养老服务体系规划明确要求养老机构信息化；中小型机构普遍还在用纸质表格和微信群管理，存在记录不可追溯、家属不放心、服药这类安全事项无人闭环跟办三个痛点。这个题目业务边界清晰、规模适合单人开发，同时能完整覆盖我大学阶段想练的技术栈（后端框架、数据库设计、鉴权安全、前端工程化）。

### Q1.3 都是你一个人做的吗？遇到最大的困难是什么？

**参考答案**：从需求分析、数据库设计到前后端实现、接口测试都是我独立完成的。最大的困难是用药任务的设计取舍：最初想"计划表 + 每日任务"分开或上定时任务，后来改成一张 `medicine_plan` 表、任务在查询时按需生成的惰性方案——它把"方案自动延续、逾期标记、停用不复活"三个需求用纯业务代码解决了，没有引入 Quartz 这种额外组件，也更符合毕业设计的体量。这个迭代过程让我体会到设计要服务于业务约束而不是堆技术。

## 二、技术选型与架构类

### Q2.1 为什么选 Spring Boot？

**参考答案**：一是自动装配、起步依赖，省去 SSM 时代大量 XML 配置，我能把精力放在业务上；二是内嵌 Tomcat、生态成熟，MyBatis-Plus、Redis、EasyExcel 都有官方 starter；三是 JDK 17 + Spring Boot 3.x 是目前企业主流版本，做毕业设计正好对齐就业技术栈。

### Q2.2 为什么前后端分离？C/S 或模板渲染不好吗？

**参考答案**：机构场景既有电脑端也有平板/手机浏览器访问，B/S 免安装；前后端分离让前端专注交互与图表渲染，后端专注接口与业务规则，用 JSON 约定契约（有完整 API 文档），开发、测试、部署解耦。我用 Vite 代理解决开发期跨域，生产可以把 dist 静态托管在任意服务器，后端只暴露 API。

### Q2.3 讲一次完整的请求链路：家属查看探访列表。

**参考答案**：前端路由 `/visit` 守卫校验 token 与角色后放行页面，页面调 `api/visit.js` 发 `GET /api/visits`；Axios 请求拦截器附加 `Authorization: Bearer <token>`；后端 `JwtInterceptor` 先验签与有效期，再查 Redis 黑名单（退出过的令牌在此被拒），然后把 userId/role 放入 ThreadLocal 的 `UserContext`，核对 `@RequireRole`（此接口允许全部角色）；进入 `VisitController.page`，`VisitServiceImpl` 判断当前是 family 角色，强制拼接 `family_id = 当前用户` 的条件分页查询，`fillNames` 二次批量查询补老人姓名/家属姓名，最后 `Result` 统一响应体包成 `{code:200,data:Page}`，前端响应拦截器取出 data 渲染表格。

### Q2.4 为什么不用 Spring Security / Shiro，而是自己写拦截器？

**参考答案**：本系统权限模型很简单——固定三角色、接口级授权，RBAC 动态角色表不是本期需求。自研方案 = `JwtInterceptor`（验签 + 黑名单）+ 自定义注解 `@RequireRole` + 业务层归属校验，总共约 100 行代码，链路完全透明可控，面试时我能讲清每一行；Spring Security 的过滤器链、ContextHolder 体系更重，学习成本花在了刀刃之外。如果以后要做按钮级权限、动态角色，再迁移 Spring Security + 权限表是值得的演进方向。（这题答"不了解 Security"就输了，要答"权衡后选择"。）

### Q2.5 MySQL 和 Redis 各存什么？为什么这么分？

**参考答案**：MySQL 存所有需要持久、可追溯的业务数据（8 张表）。Redis 只存三类"短生命周期、高频读写、可容忍丢失"的数据：验证码文本（5 分钟）、登录失败计数（首次失败起 15 分钟）、登出令牌黑名单（令牌剩余有效期）。共同点是有 TTL 天然匹配、读写频繁、丢了只是体验降级不会造成业务损失；放 MySQL 反而要建表、写清理任务。这也是"什么数据配进缓存"的一次完整实践。

## 三、登录与安全类（必考重点）

### Q3.1 JWT 里放了什么？服务端怎么验证？

**参考答案**：`JwtUtil` 用 jjwt + HS256 签发，payload 放 userId、username（subject）、role 和过期时间（24h）。验证就是拦截器里 `parseToken`：用同一密钥验签名、核对 exp——签名过不了或过期直接 401，不需要查库，这就是"无状态"。

### Q3.2 JWT 无状态有什么问题？你是怎么解决的？（本项目最核心的安全设计）

**参考答案**：无状态的另一面是"签发即有效"：用户点了退出、或者令牌疑似泄露，服务端也无法让它作废。我的方案是登出黑名单：`POST /auth/logout` 解析令牌拿到剩余有效期，把 `jwt:blacklist:{token}` 写入 Redis，TTL 与剩余有效期对齐；拦截器每次验签通过后多查一次黑名单，命中返回 401。TTL 设计让垃圾数据随令牌自然过期自动清除，无需清理任务。代价是每个鉴权请求多一次 Redis 查询，换取"登出即时生效"。

**追问：为什么不存 jti（令牌唯一编号）？**——存 jti 需要签发时写入 id，并按 id 拉黑，好处是黑名单短；我直接按令牌原文做 key，实现最直白、可用 redis-cli 演示，24h 的令牌基数有限，空间不是问题。

**追问：Redis 挂了会不会所有人都进不去？**——会，所有鉴权接口都会因查不到黑名单而报错。这是明确取舍：登录安全的强依赖换简单性；生产可加本地缓存 + 降级开关（如 Redis 不可用时放行只读接口）。

### Q3.3 图形验证码怎么实现的？为什么存 Redis？为什么要"一次性"？

**参考答案**：`AuthServiceImpl.createCaptcha()` 用 Hutool `LineCaptcha` 生成 120×44、4 字符、12 条干扰线的图片，随机 UUID 作 captchaId，文本转小写存 `captcha:{captchaId}`（TTL 5 分钟），图片以 Base64 dataURL 返回，前端直接当 `<img src>`。登录时先 GET 再立刻 DELETE——校验一次即作废，防止一个验证码被重复使用配合暴力猜解。比对用忽略大小写。开关 `app.captcha.enabled` 可关闭，便于自动化测试。

### Q3.4 登录锁定逻辑讲一下，几个细节？

**参考答案**：Redis key `login:fail:{username}`，密码错误时 `INCR`；只在计数从 0→1 时设置 `EXPIRE 15min`，所以锁定窗口**从首次失败起算、不滑动**——否则每错一次就续期，等于无限锁。达到 5 次后登录接口第一步直接拒绝（即使密码正确）；登录成功、或管理员重置等操作前都 `DEL` 清计数。**校验顺序是刻意设计的：锁定检查放最前**，锁定期间不消耗验证码——不然攻击者可以用不同验证码探测何时解锁。

**追问：INCR 和 EXPIRE 不是原子的，中间崩溃怎么办？**——理论上会留下无 TTL 的计数 key。承认这是简化实现；生产写法是 Lua 脚本合并两条命令，或启动时对 `login:fail:*` 扫尾。毕设场景 15 分钟后 Redis 自动过期或人工 `DEL` 即可恢复，README 常见问题里也写了。

### Q3.5 密码为什么用 BCrypt 而不是 MD5？

**参考答案**：MD5 快且无盐，彩虹表和 GPU 碰撞都轻松破解。BCrypt 自带随机盐（同一密码每次密文不同）、计算成本可调（默认 2^10 迭代），为"慢哈希"设计，拖库后离线爆破成本极高。Spring 的 `BCryptPasswordEncoder` 一行代码搞定，密文存 `sys_user.password`（60 字符左右，字段给了 VARCHAR(100)）。实体上 password 加了 `@JsonIgnore`，任何接口都不会把密码带出去。

### Q3.6 为什么用户名错误和密码错误提示一样？

**参考答案**："用户名或密码错误"统一文案，不暴露账号是否存在，防用户枚举。配合连错 5 次锁定，构成防暴力破解的两层。

### Q3.7 密码明文传输，安全吗？

**参考答案**：传输安全不是应用层职责，部署走 HTTPS，证书加密整条通道，这是行业常规做法（登录接口文档里注明了部署前提）。不在前端做加密传输是因为那只是混淆，解决不了中间人重放，HTTPS 才是正解。

### Q3.8 令牌 24 小时过期，为什么不用 refresh token？

**参考答案**：目标用户是机构内网环境的使用者，24h 覆盖一个完整工作日，到期重新登录即可；引入双令牌会增加 Redis/DB 存储与续签逻辑，收益不匹配。演进方向可以做：到期前静默续签 + 黑名单旧令牌，架构上已被现在的黑名单设计兼容。

### Q3.9 禁用账号、改密码后旧令牌怎么办？

**参考答案**：登录时校验 `status=0` 返回 403"账号已被禁用"。改密码和禁用**不会**使已签发的旧令牌立即失效——因为令牌里不含版本信息。如实承认这是已知边界；改进方案是在 JWT 加 `pwdVer` 声明 + 用户维度 Redis 黑名单，或拦截器回查一次用户状态（牺牲一点无状态优势）。这也说明"黑名单按令牌维度"和"按用户维度"是两种粒度的撤销能力。

## 四、权限与数据隔离类

### Q4.1 @RequireRole 的实现原理？

**参考答案**：自定义注解可标注在 Controller 方法或类上，声明允许的角色数组。`JwtInterceptor` 鉴权通过后，从 `handlerMethod` 取注解（方法级优先、类级兜底），当前用户角色不在列表就抛 403。相当于用 30 行代码复刻了一个极简声明式授权。

### Q4.2 家属越权访问别人的老人怎么办？（水平越权）

**参考答案**：接口级注解只挡"角色不对"，防不住"角色对但访问了别人的数据"，所以有第二层数据级隔离：所有涉及老人的读接口，family 角色要么走 `checkFamilyOwnership(elderId)` 校验 `elder_info.family_id` 是否等于当前用户（不等 403），要么列表查询被强制覆盖为只查自己关联的老人（护理/体征/探访/留言列表全部如此）；写接口（提交探访、留言）自动绑定当前用户为 familyId，且校验老人归属，家属连"替别人老人预约"都做不到。演示时用 family01 的 token 直接请求 family02 老人（id=2）的详情/档案/趋势，三个接口都返回 403，`test_api.js` 有对应断言。

### Q4.3 401 和 403 怎么区分？前端怎么处理？

**参考答案**：401=未登录/令牌失效（未携带、验签失败、进了黑名单），前端响应拦截器收到就清 localStorage 跳登录页；403=已登录但无权限（角色不符、越权访问、账号禁用），只弹错误提示不清登录态。前端菜单和路由 `meta.roles` 只是体验层过滤，真正防线在服务端拦截器与业务校验——"前端隐藏按钮不等于安全"，这句一定要说。

## 五、数据库设计类

### Q5.1 为什么只有 8 张表？角色、房间不单独建表？

**参考答案**：设计原则是"小数据用字段、大数据用表"。角色固定三种、房间总量几十间（机构规模）、用药任务若拆表要双表同步——这三处建表带来的联表和维护复杂度大于收益，所以用 `sys_user.role`、`elder_info.room_no/bed_no` 字段承载，`medicine_plan` 一行同时是处方和任务。老人表是业务主表，五张业务表都挂在 elder_id 上。这个取舍在答辩里反而加分：证明"建表不是越多越好"。

### Q5.2 为什么不用物理外键？

**参考答案**：一是毕设惯例、也是互联网主流做法——外键约束由业务层校验 + 必要索引保证（如 `idx_family_id`），删除老人前 Service 显式检查五张业务表有无关联数据；二是物理外键在测试数据灌入、分库演进时都是阻碍。关联完整性策略是"写时校验、读时补名"（批量二次查询填 `familyName/elderName` 等非表字段）。

### Q5.3 索引怎么设计的？

**参考答案**：只给高频查询路径建：`sys_user.username` 唯一索引（登录）、`elder_info.id_card` 唯一 + `family_id`/`status` 索引（家属过滤、列表筛选）、`care_record`/`health_record` 的 `(elder_id, 时间)` 联合索引（按老人按时间查）、`medicine_plan` 的 `(elder_id, plan_date)` 和 `(plan_date, status)`（任务查询与逾期扫描）、日志表时间索引。原则是联合索引遵循最左前缀、等值在前范围在后。

### Q5.4 讲一个你觉得设计得最巧妙的字段。（disabled）

**参考答案**：`medicine_plan.disabled`。用药任务"按需生成"意味着每天的查询会从历史任务行复制延续——那"停用计划"如果只删除未来的行，次日复制又会把它复活。所以停用时：①删除 `plan_date >= 今天` 的任务行；②把该老人该药的历史行统一置 `disabled=1`，生成逻辑的源头查询强制 `disabled=0`，复制链条被切断，历史数据完整保留作用药档案。这个字段是文档设计（"删行即停用"）被实现证伪后补上的，对应 README"对设计文档的补充说明"第 1 条，属于真实的设计迭代，很值得讲。

### Q5.5 MyBatis-Plus 有什么坑？

**参考答案**：一个典型：`updateById` 默认不更新 null 字段，而退住登记需要把 `room_no/bed_no` 显式置 NULL 表示"释放床位"。我改用 `LambdaUpdateWrapper.set(field, null)` 生成显式 SET 子句解决。这个细节在 `ElderServiceImpl.checkout`，代码注释里也写了。

## 六、核心算法：用药任务闭环（项目招牌，必考）

### Q6.1 30 秒讲清用药闭环。

**参考答案**：一张表一行 = 某位老人某天某时间点的一次服药任务。护士录入计划 → 当天插入若干"待执行"行；之后每天的查询做三件事：把早于今天仍未执行的行标"已逾期"、取当日行、当日没有就从该老人**最近一天**未停用的方案复制生成；护士喂药后点"确认执行"置已执行 + 确认时间；停用方案删未来行并把历史行置 disabled 防"复活"。

### Q6.2 为什么不用定时任务（Quartz/@Scheduled）？

**参考答案**：任务生成和逾期标记本质是"查询时顺便维护"——没人查询就不需要算，机构场景每天只有少数几个访问时刻，惰性方案零调度依赖、无并发跑批风险、逻辑全在 `listTasks` 一个方法里可单测可断点演示。"不引入组件"本身就是选型理由：复杂度要与需求匹配。

### Q6.3 逾期扫描为什么要"按真实今天"而不是查询日期比较？

**参考答案**：`listTasks` 可以查任意日期。如果把判定写成"plan_date < 查询日期"，查明天任务就会把今天还没到点的待执行行误标逾期。所以代码固定用 `plan_date < LocalDate.now() AND status=0`，这是被真实 bug 教育后定的规则，答辩讲这个细节非常加分。

### Q6.4 按需生成在并发下会不会生成重复任务？

**参考答案**：会。两个请求同时查"今天还没生成的老人"，都判空、都复制，产生重复行。如实承认，然后给改进：给 `(elder_id, plan_date, plan_time, medicine_name)` 建唯一索引 + 插入用 `INSERT IGNORE`/捕获 DuplicateKey 降级为查询，即可幂等。机构场景并发极低（同一老人的任务只有一名值班护士在看），风险可接受——但答题要表现出"知道边界在哪、怎么修"。

### Q6.5 录计划时同一天同时间点重复提交怎么办？

**参考答案**：`addPlan` 对每个时间点先按"老人+药名+当天+时间点"查重，存在则跳过，天然幂等；停用再重录会生成新任务行，历史行上次的 disabled 不影响（新行 disabled=0）。

## 七、AOP 日志 / 统一响应 / 全局异常

### Q7.1 操作日志怎么做到"零侵入"？

**参考答案**：写操作在 Controller 方法上标 `@OperLog("新增老人")`，`LogAspect` 用 `@Around("@annotation(operLog)")` 切面拦截：目标方法成功返回后组装 `SysLog`（操作人取 `UserContext`、操作描述取注解、请求方法+URI、参数 JSON、IP），try-catch 包住入库——日志写失败只 warn，绝不影响业务。异常时 `proceed()` 直接抛出，天然"只记成功操作"。演示时随便做一次新增，去日志页立刻能查到。

### Q7.2 参数记录有什么防护？

**参考答案**：序列化时跳过 `HttpServletRequest/Response` 等容器对象（防循环引用），JSON 后截断 500 字符对应表字段 `params VARCHAR(500)`。密码类写操作（修改密码）也走日志，生产环境还应做敏感字段脱敏——这是可主动提的改进点。

### Q7.3 统一响应体 Result 和全局异常解决了什么？

**参考答案**：所有接口返回 `{code,message,data}`，HTTP 状态与业务 code 对齐（401/403/404 各归其位，其余业务错 400）。业务代码只 `throw new BusinessException(403,"…")`，由 `@RestControllerAdvice` 统一转 JSON；`MethodArgumentNotValidException`（@Valid 参数校验失败）取第一条字段消息转 400；唯一键冲突 DuplicateKey 转"数据已存在"；其余 Exception 兜底 500 且不泄漏堆栈。Controller 里没有一行 try-catch。

### Q7.4 线程上下文为什么用 ThreadLocal？要注意什么？

**参考答案**：把当前用户放进 `UserContext`（ThreadLocal），Service/AOP 随处可取"我是谁"，方法签名不用层层传。风险是线程池复用导致串号/泄漏，所以拦截器 `afterCompletion` 必须 `UserContext.clear()`——这是 ThreadLocal 三件套（set/get/remove）的标准实践。

## 八、前端类

### Q8.1 登录态怎么管的？刷新页面为什么不掉？

**参考答案**：Pinia store 是内存态，token 和 user 同时落 localStorage；应用启动时 store 从 localStorage 恢复。退出时调服务端 logout 拉黑后清两处。刷新不掉是因为状态源在 localStorage，路由守卫每次读它判断。

### Q8.2 路由守卫和菜单过滤讲一下。

**参考答案**：路由 `meta.roles` 声明各页面允许角色；`beforeEach` 三段判断：无 token → /login；已登录访问 /login → 首页；角色不在 meta.roles → 回默认首页（未设 403 页，属简化）。侧边栏菜单同样按角色过滤生成，家属登录后根本看不到用户管理、用药任务等入口。

### Q8.3 Axios 封装做了什么？

**参考答案**：单实例 baseURL `/api`、15s 超时。请求拦截附加 Bearer token；响应拦截把 code=200 的数据放行、401 清登录态跳登录、其余弹 message；特殊处理 `Blob`（Excel 下载流直接返回）；另配 `downloadFile()` 工具把 Blob 转 a 标签触发下载。错误消息统一由拦截器弹出，页面代码只管业务分支。

### Q8.4 Excel 导出的完整链路？

**参考答案**：后端 Controller 直接写 `HttpServletResponse`：设置 `Content-Type` xlsx + `Content-Disposition: attachment; filename*=utf-8''…`（URL 编码解决中文文件名乱码），`EasyExcel.write(out, ElderExportVO.class).sheet().doWrite(list)`；导出 VO 用 `@ExcelProperty` 定义表头，查询条件与列表页共用同一 Service 方法保证"导出=所见"。前端以 `responseType:'blob'` 请求，拿到流触发下载。

### Q8.5 ECharts 图表有哪些？数据接口对应？

**参考答案**：首页看板四个接口驱动：`stats/overview`（4 张统计卡：入住率=在住/总数×100 保留一位、今日护理/探访数、逾期任务数）、`age-distribution`（环形图，五个年龄段）、`activity-trend?days=30`（双折线：护理/探访）、`elder/{id}/health-trend`（体征折线，血压按收缩/舒张拆两条线，metric 白名单防注入）。趋势接口在服务端按日期序列补 0，前端拿到即是等长数组；窗口 resize 时 `chart.resize()`，组件卸载 `dispose` 防泄漏。

## 十、开放题与"挖坑"题

### Q10.1 这个项目还有哪些不足 / 重做会改什么？（必考，先自查再答显得诚实）

**参考答案**（挑 4~5 条，全部有代码依据）：
1. **撤销粒度**：改密/禁用不即时踢人 → 需用户维度黑名单（令牌加版本声明）；
2. **并发边界**：按需生成任务理论可重复 → 唯一索引 + INSERT IGNORE 幂等；
3. **INCR+EXPIRE 非原子** → Lua 脚本；Redis 未启动时全接口不可用 → 降级策略；
4. **权限模型静态**：三角色写死在注解，无动态权限表；前端只到页面级，无按钮级；
5. **敏感日志脱敏**：改密码操作的参数会进 sys_log，生产应掩码；
6. **无自动化 CI / 无监控告警**，操作日志只增不清理。
每条都"问题 + 方案 + 为什么本期不做"三段式，落点是"知道边界、演进路径清晰"。

### Q10.2 用户量涨 100 倍怎么改？

**参考答案**：应用层无状态可水平扩容（多实例 + Nginx）；MySQL 读写分离、慢查询治理（列表全部走索引与分页）；验证码/黑名单本就适合 Redis，可上哨兵；统计看板改预计算/缓存 5 分钟；日志异步化（消息队列或 @Async）避免同步写库拖慢响应。

### Q10.3 老师问"你这个项目技术含量在哪里？"

**参考答案**：不在"用了什么框架"，在三个设计决策：①用药任务的惰性生成方案（用一张表 + 一个 disabled 标志位解决"自动延续/逾期标记/停用不复活"三角约束，零调度组件）；②Redis 三件套补足 JWT 无状态的撤销缺陷（验证码一次性防重放、非滑动锁定窗口、黑名单 TTL 与令牌对齐）；③接口级鉴权 + 数据级归属校验的两层越权防线。每个都能现场指到代码、现场演示。

### Q10.4 为什么安全数据放 Redis 不怕丢？（选型反问）

**参考答案**：逐类看丢失后果：验证码丢了→用户刷新重领，无业务损失；计数丢了→提前解锁，仍有 5 次阈值兜底；黑名单丢了→最坏情况旧令牌恢复有效直到自然过期（上限 24h），且前提是"攻击者持有了已登出令牌"这一小概率组合。三类全满足"可容忍丢失 + 有第二道防线"，所以敢放 Redis；反例是老人档案——绝不可能放。

## 十一、求职面试专章：我遇到的后端问题与解决（按真实修复痕迹整理）

> 用法：面试问"项目里遇到什么困难/印象最深的 bug"，从 13 个里**挑 3 个背熟**（推荐 ①停用复活 ②逾期窗口 ③登出黑洞——全是纯逻辑问题，能画白板）。讲法固定五步：**场景 → 现象 → 根因 → 解法（代码位置）→ 复盘一句**。C 组是"承认局限 + 给修法"，专门应对追问深挖。

### A. 业务逻辑类（含金量最高，优先讲）

**① 停用用药计划"复活"bug（招牌题，对应 disabled 字段）**
- 场景：用药任务按需生成——某天查不到任务时，从该老人最近一天的任务行复制延续方案。
- 现象：护士"停用"某计划（删掉今天及以后所有任务行），**第二天任务又出现了**。
- 根因：删除只消了未来行；按需生成的复制源头是"plan_date 最大的历史行"，历史行还在，复制逻辑把它当"在用药方案"延续回来。是"两个正确的设计点（惰性生成 + 删行即停用）互相打架"。
- 解法：`medicine_plan` 加 `disabled` 标记；`disablePlan` 删未来行 + 历史行置 1；`generateTasks` 找复制源头时强制 `disabled=0`，链条即断；历史数据完整保留作用药档案（`MedicinePlanServiceImpl`）。
- 复盘：设计冲突比设计缺陷更难发现，因为每一部分单看都对；修复选了"最小侵入加一个位"而不是重构两套表。

**② 逾期扫描误标（时间基准 bug）**
- 现象：查"明天"的任务列表，今天还没到点的待执行任务全变成了"已逾期"。
- 根因：逾期条件写成了 `plan_date < 查询日期`——把"相对查询基准"当成了"相对现实世界"。
- 解法：扫描固定 `plan_date < LocalDate.now() AND status=0`，与用户查哪天无关（`listTasks` 内有注释留档）。
- 复盘：凡带"过期/超时"语义的逻辑，先问一句"时间基准是什么"；测试用例要显式包含"查未来/过去日期"。

**③ JWT 登出"黑洞"（无状态令牌无法撤销）**
- 现象：点退出只清了前端 localStorage，用抓包拿旧 token 重放，接口照样返回数据。
- 根因：JWT 自包含 + 服务端无会话，签发出去的 24h 内永远有效——这是机制属性不是编码错误。
- 解法：登出时把 `jwt:blacklist:{token}` 写入 Redis，TTL 精确等于令牌剩余有效期（过期了自然清，不留垃圾）；拦截器在验签通过后追加黑名单检查，命中 401（`AuthServiceImpl.logout` + `JwtInterceptor` 第 2 步）。
- 复盘：方案成本是"每请求多一次 Redis GET"，用"登出必须即时失效"的业务要求论证值得；再往上就是 jti + 短令牌双 token，讲得到位即可不必炫。

**④ 登录锁定的"滑动窗口"陷阱**
- 现象（设计推演发现）：如果每次失败都重置 15 分钟 TTL，锁定永远到不了期，等于给攻击者无限次机会。
- 解法：`RedisService.increment` 只在计数 0→1 时设 EXPIRE，窗口**从首次失败起算、只累加不续命**；达 5 次直接拒绝（此时密码正确也不行），成功登录再 `DEL` 清零。校验顺序也是刻意的：**锁定检查放验证码之前**，否则锁定期间会白白消耗一次性验证码，还给攻击者提供了"解锁时机"探测面。
- 复盘：限流类计数要分清固定窗口/滑动窗口语义；这是"设计评审阶段就掐掉"的故事，比线上救火更显功力，可以主动说"这个我是推演发现的，不是踩坑"。

**⑤ 验证码重放**
- 风险：一次性验证码若"校验通过才删"，失败尝试不删，同一 captchaId 可无限试。
- 解法：`checkCaptcha` 里 GET 之后**无论对错先 DEL 再比对**，天然一次性；文本统一小写存储、输入 trim+toLowerCase 比对，避免"看图输大写被判错"的伪 bug。
- 复盘：安全功能要站在攻击者视角过一遍"我能重复利用什么"。

### B. 框架与实现坑类（体现排错能力）

**⑥ MyBatis-Plus updateById 不吃 null（退住释放床位）**
- 现象：退住登记调 `updateById`，status/checkout_time 都改了，room_no/bed_no 却没置空——床位看似仍被占。
- 根因：MP 默认字段策略 NOT_NULL，null 字段直接不进 SET 子句（这是乐观更新的设计，不是 bug）。
- 解法：`ElderServiceImpl.checkout` 改用 `LambdaUpdateWrapper.set(ElderInfo::getRoomNo, null)…` 显式生成 SET。
- 复盘：ORM 的"便利性"和"显式性"要分开看；当时也评估过全局 `update-strategy=IGNORED`，会影响所有更新语句，放弃。

**⑦ selectBatchIds 传空集合直接拼出非法 SQL**
- 现象：一条 nurse_id 为空的护理记录进列表页，接口 500：`IN ()` 语法错误。
- 根因：`fillNames` 把 elder_id、nurse_id 各自去重后批量查，空集合没防护。
- 解法：空集合短路返回（`CareRecordServiceImpl.fillNames` 有注释留档），后续所有批量补名都先判空。
- 复盘：给"框架方法不防边界"的教训——封装工具前先想空值语义。

**⑧ Excel 中文文件名乱码**
- 现象：导出正常，下载文件名成 `????.xlsx`。
- 根因：`Content-Disposition: filename=` 默认按 ISO-8859-1 解读，中文直接坏。
- 解法：`filename*=utf-8''` + `URLEncoder.encode(...)`，再把 `+` 换回 `%20`（URL 编码把空格编成 +，RFC 5987 场景要还原）——`ElderController.setExcelResponseHeader`。
- 复盘：HTTP 头的字符集是经典盲区；同类还有响应流没设 utf-8。

**⑨ 切面参数序列化把日志写炸**
- 现象（预防性）：`@Around` 里把方法 args 全量 Jackson 序列化时，`HttpServletRequest` 参数会触发循环引用/超大 JSON。
- 解法：`LogAspect.buildParams` 过滤 request/response 类型再拼接，JSON 截断 500 字符对齐 `params VARCHAR(500)`，整个日志写入再套 try-catch——日志失败只 warn，绝不影响业务。
- 复盘：横切代码要按"最坏输入"设计；同时确立"操作日志只记成功"（proceed 抛异常自然不记）。

**⑩ 密码字段随实体外泄**
- 现象：接口自测发现 `/auth/me`、用户列表把 `password` 密文一起返回。
- 解法：`SysUser.password` 加 `@JsonIgnore`（序列化层一刀切，不怕哪天忘了换 VO）；登录响应 `LoginVO` 只带非敏感字段。
- 复盘：敏感字段隔离优先在**出口**统一做，不依赖每个接口自觉。

**⑪ ThreadLocal 串号隐患**
- 风险：`UserContext` 存当前登录用户，Tomcat 线程复用，忘记清理会把上一个请求的身份漏给下一个。
- 解法：拦截器 `afterCompletion` 无条件 `UserContext.clear()`——它和 set/get/remove 三件套一样是纪律不是选项。
- 复盘：任何 ThreadLocal 方案都要当场给出"在哪清理"，否则面试等于自曝。

### C. 设计权衡与已知局限（追问深挖时的标准应对：承认 + 给修法 + 说约束）

**⑫ 按需生成的并发重复**：两个请求同时查"当天无任务"的老人 → 都判空、都复制 → 重复行。当前无唯一索引（`idx_elder_date` 是普通索引），如实承认；修法：`(elder_id, medicine_name, plan_date, plan_time)` 唯一索引 + 插入捕获 `DuplicateKeyException` 降级为查询（全局异常已有该 handler），即可幂等；约束是机构并发极低，本期未上。

**⑬ INCR+EXPIRE 非原子**：两命令之间进程崩溃会留下永不过期的计数 key（"永久锁定"）。承认；修法 Lua 脚本或先 `SET key 1 EX 900 NX`；并补充"人工 `redis-cli DEL login:fail:x` 即可恢复"说明可控。同类还有：Redis 是鉴权强依赖（拦截器每请求查黑名单，Redis 宕机全接口 500）→ 降级开关/本地短缓存是演进方向；改密后旧令牌不即时撤销 → 令牌加 `pwdVer` 声明 + 用户维度黑名单可解决，讲清"黑名单按令牌 vs 按用户"是两种撤销粒度。

### 收尾三句话模板（任选问题讲完时用）
